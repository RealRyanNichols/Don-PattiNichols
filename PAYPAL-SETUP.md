# PayPal checkout and donation reporting

The website links to Don's existing PayPal Donate checkout. Opening checkout,
recording a gift intention, returning to the website, and receiving a verified
payment are different events. None of the first three is a receipt.

## Current status

- `lib/paypal.ts` builds `paypal.com/donate/` links using the existing merchant.
- `gift_intents` records anonymous checkout choices for the admin. These are
  intentions, not money raised or confirmed monthly gifts.
- `/give/thank-you` is an optional follow-up page. It does not verify payment.
- The payment webhook is dormant unless its server credentials are configured.
  Its GET endpoint reports configuration presence only, not a working payment
  connection or successful reconciliation.
- Check PayPal's transaction records to verify actual gifts. Public figures come
  from recorded donations through the existing aggregate database functions.

## Confirm the notification mechanism before connecting it

The previous version of this guide assumed that creating a REST app and adding
its webhook would report payments from the existing Donate links. That has not
been established and must not be treated as a working integration.

[PayPal's webhook documentation](https://developer.paypal.com/api/rest/webhooks)
says that a webhook receives events associated with its specific app. The Donate
links here do not create a payment through that REST app. Adding credentials
alone therefore does not prove that these gifts will generate its capture events.

With access to Don's existing PayPal account, confirm the supported notification
mechanism for this specific Donate checkout. PayPal documents
[Instant Payment Notification](https://developer.paypal.com/api/nvp-soap/ipn/IPNIntro)
for Payments Standard transactions and
[account or per-payment listener configuration](https://developer.paypal.com/api/nvp-soap/ipn/IPNSetup).
That is a separate protocol: do not point IPN at the existing REST webhook.
Alternatively, a deliberate REST checkout integration would need to create
payments through the same app as its webhook. Preserve the existing recipient.

## Requirements before enabling automatic reporting

1. Verify that a supported notification is generated by the actual checkout in
   use, for both one-time and monthly gifts where supported.
2. Validate notifications and the receiving merchant before storing a payment.
3. Verify transaction deduplication against the live database constraint. Use
   stable fund/item metadata instead of relying on human-readable descriptions.
4. Reject unsupported currencies or explicitly convert them; a non-USD amount
   must never be stored as though it were USD.
5. Reconcile refunds, partial refunds, and reversals with their original payment
   and designation. Reduce quantities correctly and handle repeated deliveries.
6. Test with sandbox transactions first, including rejected signatures, repeated
   notifications, storage failures, monthly renewals, and refunds. Do not insert
   simulator events into the production donation ledger.
7. Verify any authorized live test against the PayPal record, the private admin
   record, and public aggregate totals. Configuration or a successful simulator
   request alone does not prove live settlement reporting.

The existing webhook still needs this integration and reconciliation work. Do
not enable it merely to make the configuration check turn green.

## Server configuration reference

The existing REST webhook reads these server environment variables:

| Variable                    | Purpose                                          |
| --------------------------- | ------------------------------------------------ |
| `PAYPAL_CLIENT_ID`          | Client ID for the app that processes the payment |
| `PAYPAL_CLIENT_SECRET`      | Secret for that same app                         |
| `PAYPAL_WEBHOOK_ID`         | Verified listener's webhook ID                   |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only access to the existing database      |

`PAYPAL_ENV=sandbox` selects the sandbox API; the default is live. Never mix
sandbox events with production money records. Secrets belong only in the
appropriate server environment, never in source, screenshots, or messages.
No credentials, merchant, authentication, or database schema are changed by this
guide. Do not apply `supabase/schema.sql`; it is an early reference schema.

When eventually configured, the existing REST listener URL is:
`https://www.donandpatti.com/api/paypal/webhook`.

[PayPal retries failed REST webhook deliveries up to 25 times over three days](https://developer.paypal.com/api/rest/webhooks/rest/).
Retries are not indefinite. Review delivery history and reconcile missed events;
do not assume old gifts will appear after credentials are added.

## Recording verified gifts meanwhile

Don and Patti can use **Money → Write down a gift myself** in the existing admin
for a gift verified in PayPal, a cash gift, or a check. Check for an existing
record first and retain a private transaction reference so later automation does
not count the same gift again. Never record a checkout click as revenue.

Preserve all earlier manual gift records and their private notes. Do not add
them again when connecting a new reconciliation workflow.
Donor details stay in the private admin. Public pages use aggregate reporting.
